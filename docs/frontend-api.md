# Frontend ↔ GE360 Rilievi Backend contract

The current `ge360-open-plan3d` frontend sends payload **version 4**. Sketch coordinates are indicative; `lengthCm`, opening width/offset and user-entered heights remain authoritative.

## Runtime flow

1. `POST /api/v1/plans` stores immutable `raw/original.json`. `planId` may be supplied by the frontend or generated by the backend.
2. `POST /api/v1/plans/{planId}/process` returns immediately with `QUEUED` and a `jobId`.
3. Poll `GET /api/v1/jobs/{jobId}` or `GET /api/v1/plans/{planId}`. States are `RAW`, `QUEUED`, `PROCESSING`, `PROCESSED`, `NEEDS_REVIEW`, `ERROR`.
4. Retrieve `processed`, `preview`, `png`, `svg`, `dxf`, `pdf` and `3d` once processing has completed.

`POST /api/v1/plans/refine` remains as a compatibility route for the current frontend: it saves RAW and queues the same processing pipeline.

## Versions

`POST /reprocess` never overwrites an older result. Outputs are kept under `versions/001`, `002`, etc. `GET /api/v1/plans/{planId}/versions` lists version metadata. Old artifacts remain addressable, for example `GET /api/v1/plans/{planId}/versions/1/pdf` and `/versions/1/processed`.

## Authentication and CORS

When `GE360_API_KEY` is non-empty, protected routes require `X-GE360-API-Key`. If it is empty, the server runs in explicit local-development mode and logs a warning. No secret is stored in the repository.

Allowed browser origins are configured with comma-separated `GE360_CORS_ORIGINS`. Production should list exact origins rather than `*`.

## 3D viewer

The backend always produces independent `plan3d.json`. A minimal Three.js viewer is served from `/viewer3d/`; open it with `?plan=/api/v1/plans/PLAN_ID/3d`. It supports orbit, pan, zoom, top view, perspective and reset, and renders wall openings from the GE360 model.
